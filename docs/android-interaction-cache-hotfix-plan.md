## Motion and gesture implementation

1. Apply Android WebView zoom policy at the existing Android plugin load hook where system text scaling is configured. Remove the Android CSS pinch allowance while retaining vertical pan, horizontal tab-strip scrolling and control-specific drag behavior. Keep browser and Windows zoom/reflow coverage.
2. Reproduce tap drift, diagonal motion, small horizontal drags and a fast tap during settling using real touch input. In the Library pager defer movement until horizontal intent is clear, account for the dead zone before tracking the finger, and keep browser-native vertical momentum. Once a drag, scroll, hold or second pointer claims a sequence, ensure the synthesized click cannot activate the original or newly exposed surface. Preserve clean taps, intentional holds, keyboard activation, scrubbing, and slider input. Reuse existing gesture cancellation and compatibility-click handling where they fit.
3. Drive content settle, active tab and underline from the same navigation state. Keep interpolation interruptible from the current visual position. Both canceled drags and rapid changes should settle on a stable pane, with one focusable tabpanel and no stale animation callbacks. Check cancellation when an overlay takes focus, a press interrupts a settle, or the app backgrounds. Use bounded transforms and opacity, and retain reduced-motion behavior. Use the existing scroll anchors to return from album, artist and playlist details, and keep the Library and player motion direction consistent with Back.
4. Verify the pane and tab strip after layout or language changes. Check the fixed header and mini-player in EN/ES, with Android display and text scaling and in light/dark themes. Keep Local Music's visual identity and use Samsung Music as the reference for responsiveness and continuity.

## Storage, cache and data transfer

At roughly 0:18–0:31 and 0:45–0:57 in the Local Music recording, Android reports **114 MB Data and 3.35 MB Cache for Local Music** and **3.16 MB Data and 103 MB Cache for Samsung Music**. The earlier Local Music App info screen shows “No data used” under Mobile data. The comparison measures Android's storage categories at that moment. It cannot attribute individual files or measure app memory, latency, or how much each app has cached for the same library.

Code review confirms Android's [`MusicReader`](../src-tauri/plugins/native-music/android/src/main/java/MusicReader.kt) writes regenerable 64 and 512 px PNGs under `context.dataDir/artwork`. The [Rust artwork resolver](../src-tauri/src/artwork.rs) also uses app data, derives additional sizes, returns base64 data URLs and prunes toward a 128 MiB ceiling on some write paths. The [WebView already has a 32 MiB artwork cache](../src/components/artworkCache.ts), measured in estimated decoded image bytes, with four concurrent requests and in-flight deduplication. The current Library index already coalesces in-flight reads and virtualizes complete metadata. Target redundant disk, decode, and bridge work before expanding the cache budget.

1. Measure Android cache/data directory sizes by category on an isolated test fixture. Compare cold launch, warm relaunch, rapid scrolling and a repeated tab/detail/player walkthrough using counts for source artwork reads, encodes, artwork bridge requests and payload bytes. Record time to interactive Library, first visible artwork, and frame times on the same device and fixture before and after changes. Collect aggregate diagnostics only.
2. Move regenerable Android artwork into one app-private cache namespace shared by Kotlin and Rust. Migrate legacy artwork lazily or in bounded background work, preserving keys so an upgrade can reuse entries. Limit migration to recognized generated artwork, use atomic publication and keep a legacy entry until its cache copy is usable. Treat cache clearing or eviction as a cache miss. Leave the catalog database, listening journal, source audio and its access grants, playlist membership, queue, settings, and exported or frozen Recaps in their owned storage. Verify available source recovery and graceful fallback for unavailable audio.
3. Bound writes, bytes and request concurrency across both Android artwork writers, including import and lazy derivatives. Favor visible images and the active player. Derive only sizes used by the app, deduplicate concurrent work by source identity and size, and warm the next visible slice within a small budget. Reuse the existing WebView memory cache and validate eviction and artwork invalidation. Final disk size and encoding choices should follow measurements. Measure base64 transfer first and consider a bounded local artwork response only if bridge payload still dominates. Keep source URIs and filesystem paths out of UI payloads.
4. Reuse native catalog metadata and lookup tables while their revision is current. Profile full-index calls, playlist/search requests, and group lookups to find duplicate work. Preserve complete continuous scrolling and existing search/sort results. Share an existing ready revision and in-flight results where possible, and invalidate after imports, visibility changes and organization edits. Keep durable catalog ownership in SQLite.
5. Reuse the export scene at a smaller preview size if measurements confirm PNG encoding or decoding dominates. Generate the requested full-size PNG on demand, and keep short-lived render reuse scoped to the current recap, format, language and privacy revision. Recheck privacy before Save or Share and release intermediate blobs on close or invalidation.
